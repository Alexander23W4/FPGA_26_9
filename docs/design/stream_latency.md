## 独立回传读口（2026-10-17）

新帧写满 `double_buf` 后，`back_reader` 立即顺序读取 65536 像素，经过独立的 `out_arr` 和
`back_stream` 进入 S2MM。无反压约 2.60 ms，不再等待 HDMI 帧边界或图像扫描窗口。
HDMI 继续用另一读口按 800×525 扫描，两条路径分别锁存本帧显示参数。

仍只有两个 bank。HDMI 开启时，写下一帧前必须等 HDMI 切离目标 bank，且回传端不再占用它。
HDMI_EN=0（编号 0x04）关闭后，显示读锁释放，写端不再等待 HDMI；只保留回传端的缓存保护。
上板比较开关两种状态的连续流计时，能直接看到 HDMI 节流的影响；切换当帧包含串口控制开销，应跳过。

## 上板测“回传启动 N → 下一帧处理完成写满缓存”

重新综合 PL、构建 PS、烧录，重启 GUI 并刷新页面，选择流文件夹。
收到第二帧起，GUI 流状态会附加：

```text
回传启动→下一帧写满 xx.xx ms（写端反压 yy.yy ms）
```

计时完全在 PL 的 clk 域完成，包含回传、网口往返、PC 调度、下一输入的算法计算和缓存等待，
不依赖 PC/PS 时钟同步。起点是 `back_reader` 为新输入帧锁存读 bank 的时钟沿；终点是
下一帧第 65536 个像素写入 `double_buf` 的时钟沿。配置重绘不会重新启动此计时。
反压值只累计这个区间内 `hdl_valid && !hdl_ready` 的周期，不包括算法尚未提供像素的时间。
选图间停顿和手动配置操作也会进入该跨帧区间；比较性能时观察配置稳定后的连续流。

| 寄存器编号 | 物理地址 | 含义 |
| --- | --- | --- |
| 0x33 | 0x440000CC | 区间周期数 |
| 0x34 | 0x440000D0 | 写端受阻周期数 |
| 0x35 | 0x440000D4 | 完成计时的序号；0 表示尚无有效区间 |

毫秒 = 周期数 / 25200。32 位周期计数约 170 秒回绕；正常连续流远小于这个区间。
数值随网口图像一起回传，无额外串口请求；UART R 也可手动读到这三个寄存器。

千兆网络、无软件开销、无 HDMI 阻塞的周期/线路下限约 10.5～11.6 ms。
若 HDMI 刚开始扫描旧 bank，下一帧的结果约 7.9～9.0 ms 后准备写入，但目标 bank 要到
16.67 ms 才释放，最终约 19.3 ms 写满。实际网口吞吐和软件耗时需要以本次计时实测。

| 环节 | 时间 | 性质 |
| --- | --- | --- |
| PC 到板端：64 KiB 输入 | 百兆 5.24 ms；千兆 0.52 ms | 仅有效数据的线路下限 |
| PS 收包校验、Cache 维护、DMA 配置 | 暂预留 1～5 ms | 软件预算，待测 |
| MM2S、解包、去噪、Otsu 帧缓存收满 | 约 2.61 ms | 流水重叠，不能逐模块重复相加 |
| Otsu 阈值计算 | 约 0.02～1.15 ms | 随非空灰度桶数量变化；当前手动模式也等待计算结束 |
| 帧缓存重放、分割/轮廓、显示缓存写满 | 约 2.61 ms | 理想一像素一拍，含少量收尾 |
| 独立读缓存、颜色计算并进入 S2MM | 约 2.60 ms | 连续 65536 像素，不扫描边框；反压会延长 |
| 写端等待目标 bank 释放 | 依 HDMI 相位及回传占用而定 | 已包含在实际写满时间中，不能再机械相加 |

## 现在可以测到什么

每帧状态内含 PS 的三个分段耗时（A9 单调全局计时器）：

- `receive`：输入命令接收开始，到输入图像字节收齐，包含网络接收过程。
- `setup`：输入字节收齐，到 DMA 启动；包含输入 CRC、Cache 操作和 DMA 配置。
- `pl_to_ddr`：DMA 启动，到 PS 观察到本帧 S2MM 完整接收；包含 PL 计算、缓存等待和独立回传。

GUI 同时显示网络事务总耗时，以及最近一次 Canvas 的等待时间和提交调用耗时。
Canvas 提交耗时不等于屏幕实际呈现耗时，PC 与 PS 的绝对时钟也没有同步。
此处只传各设备内部的时长，避免把未同步的时间戳直接相减。

端到端显示延迟与收发 FPS 不等价：下一帧不等待 GUI 绘制；绘制落后时仅保留最新完整帧。
浏览器将后续输入提前上传到 Python 的有界队列，最多保留 4 帧待发（256 KiB），另允许最多 8 帧在途。
Python 使用独立发送与接收线程；允许最多 8 帧在途，不等上一帧完整回传就发送下一输入。
板端 4 个输入槽与 3 个输出槽独立管理；下一帧 DMA 可与上一帧 TCP 回传重叠。
队列耗尽时才等待浏览器补帧；结果预览只保留最近 2 帧，Worker 与主线程之间也限制待显示数量。
参数更新先暂停 Python 调度并排空所有已派发帧，更新后继续使用已缓存的原始输入；显示模式在每帧出队时确定。
停止丢弃待发送输入并让所有在途帧完成，浏览器失联 30 秒后停止会话并释放传输锁。
模式切换帧可能额外请求一次重绘/回传；参数更新时的串口操作也应单独计时。

## 存储与完成条件

流：PL → S2MM → DDR → TCP → Python 内存 → Worker → Canvas，无 BIN/PNG 落盘。
PS 使用 `TCP_WRITE_FLAG_COPY`。整帧已复制到 TCP 管理的内存后 DDR 才可复用；
TCP 自己保留重传数据。PC 发送下一输入不再以完整回传为前提；只受在途容量、TCP 接收窗口及 DDR 空间约束。
不发送应用层 RECEIVED/DONE。
单图/全显示仍保存 BIN/PNG，并在保存校验后 SAVED/DONE，保护原来的文件保存流程。
