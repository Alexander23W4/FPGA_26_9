# 连续流延迟估算与实测边界

日期：2026-10-17。以下为当前 RTL 的周期计算和软件时间预算，未测量板卡端到端延迟。
条件：256×256 灰度输入（65,536 字节），RGBA 输出（262,144 字节），PL/pclk=25.2 MHz；
显示模式稳定，PL/DMA 正常，无长期反压，无磁盘保存或逐帧串口状态回读。

## PC 发出一帧，到 S2MM 写满板端 DDR

| 环节 | 时间 | 性质 |
| --- | --- | --- |
| PC 到板端：64 KiB 输入 | 百兆 5.24 ms；千兆 0.52 ms | 仅有效数据的线路下限 |
| PS 收包校验、Cache 维护、DMA 配置 | 暂预留 1～5 ms | 软件预算，待测 |
| MM2S、解包、去噪、Otsu 帧缓存收满 | 约 2.61 ms | 流水重叠，不能逐模块重复相加 |
| Otsu 阈值计算 | 约 0.02～1.15 ms | 随非空灰度桶数量变化；当前手动模式也等待计算结束 |
| 帧缓存重放、分割/轮廓、显示缓存写满 | 约 2.61 ms | 理想一像素一拍，含少量收尾 |
| 等待 HDMI 帧边界 | 0～16.67 ms | 首帧启动可能立即进行；后续取决于到达相位 |
| 新帧边界到回传图像窗口首像素 | 3.56 ms | (112×800+192)/25.2 MHz |
| 图像首像素到末像素并进入 S2MM | 约 8.11 ms | (255×800+255)/25.2 MHz；含行间空白 |

不计软件开销及额外反压，这一段约为百兆 22.2～40.0 ms、千兆 17.4～35.3 ms。
考虑软件后的初步预算：百兆约 25～50 ms，千兆约 20～45 ms。
当前回传共享 HDMI 扫描路径，等待帧边界与扫描到图像末尾合计约 11.7～28.3 ms。

浏览器回调在下一次重绘前执行，通常跟随屏幕刷新率：
[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。

## 现在可以测到什么

每帧状态内含 PS 的三个分段耗时（A9 单调全局计时器）：

- `receive`：输入命令接收开始，到输入图像字节收齐，包含网络接收过程。
- `setup`：输入字节收齐，到 DMA 启动；包含输入 CRC、Cache 操作和 DMA 配置。
- `pl_to_ddr`：DMA 启动，到 PS 观察到本帧 S2MM 完整接收；包含 PL 计算、HDMI 等待和扫描。

GUI 同时显示网络事务总耗时，以及最近一次 Canvas 的等待时间和提交调用耗时。
Canvas 提交耗时不等于屏幕实际呈现耗时，PC 与 PS 的绝对时钟也没有同步。
此处只传各设备内部的时长，避免把未同步的时间戳直接相减。

端到端显示延迟与收发 FPS 不等价：下一帧不等待 GUI 绘制；绘制落后时仅保留最新完整帧。
本地预取最多一帧；Worker 与主线程之间的待显示数据也限制数量，不无限排队。
模式切换帧可能额外请求一次重绘/回传；参数更新时的串口操作也应单独计时。

## 存储与完成条件

流：PL → S2MM → DDR → TCP → Python 内存 → Worker → Canvas，无 BIN/PNG 落盘。
PS 使用 `TCP_WRITE_FLAG_COPY`。整帧已复制到 TCP 管理的内存后 DDR 才可复用；
TCP 自己保留重传数据。PC 收齐并校验通过后发送下一输入，不发送应用层 RECEIVED/DONE。
单图/全显示仍保存 BIN/PNG，并在保存校验后 SAVED/DONE，保护原来的文件保存流程。
